## 3. The topology data model

### Go — `/Users/robinhultman/dev/intropy/tooling/intropy-cli/internal/topology/topology.go`

Important correction to your framing: the v1 document is **not** a `nodes[]`/`edges[]` document. It is `components[]` with **wiring inlined on each component** (that's the "inline-edge schema"), plus top-level `topics[]`/`connectors[]` as lookup tables. React Flow's nodes/edges are derived client-side.

```go
const (
	APIVersion = "topology.intropy.io/v1"
	Kind       = "SystemTopology"
)

type Topology struct {
	APIVersion string      `json:"apiVersion"`
	Kind       string      `json:"kind,omitempty"`
	System     string      `json:"system"`
	Components []Component `json:"components,omitempty"`
	Topics     []Topic     `json:"topics,omitempty"`
	Connectors []Connector `json:"connectors,omitempty"`
	// APIs, and each component's Provides/Consumes below, are the contract
	// (request/response) surfaces. Their element shape is not yet finalized,
	// so they are parsed opaquely: preserved for round-tripping to the
	// frontend without asserting a schema the CLI does not yet render.
	APIs []json.RawMessage `json:"apis,omitempty"`
}

type Component struct {
	Name       string         `json:"name"`
	Kind       string         `json:"kind"`
	Subscribes []TopicRef     `json:"subscribes,omitempty"`
	Publishes  []Publication  `json:"publishes,omitempty"`
	Connectors []ConnectorUse `json:"connectors,omitempty"`
	// Provides/Consumes are contract surfaces, parsed opaquely (see APIs).
	Provides []json.RawMessage `json:"provides,omitempty"`
	Consumes []json.RawMessage `json:"consumes,omitempty"`
}

type TopicRef struct {                 // subscribe edge
	PubSub string `json:"pubsub"`
	Topic  string `json:"topic"`
}

type Publication struct {              // publish edge
	Port   string `json:"port,omitempty"`   // component output port
	PubSub string `json:"pubsub"`
	Topic  string `json:"topic"`
}

type ConnectorUse struct {
	Connector string `json:"connector"`
	Direction string `json:"direction"` // "in" | "out"
}

type Topic struct {
	PubSub      string   `json:"pubsub"`
	Topic       string   `json:"topic"`
	Contract    string   `json:"contract,omitempty"`   // &lt;-- the ONLY message/contract field today
	Publishers  []string `json:"publishers,omitempty"`
	Subscribers []string `json:"subscribers,omitempty"`
}

type Transport struct {
	Type           string `json:"type"`
	SupportsInput  bool   `json:"supportsInput"`
	SupportsOutput bool   `json:"supportsOutput"`
}

type Connector struct {
	Name           string    `json:"name"`
	ExternalSystem string    `json:"externalSystem,omitempty"`
	Transport      Transport `json:"transport"`
	Directions     []string  `json:"directions,omitempty"`
	UsedBy         []string  `json:"usedBy,omitempty"`
}

// Entry = one system's topology + the workspace dir, flattened for the API.
type Entry struct {
	Path string `json:"path"`
	Topology
}

func Decode(r io.Reader) (*Topology, error) // strict: apiVersion mismatch = error, leading noise = error
```

### The key design decision (v0.4): message-shape metadata is parsed but deliberately **not** surfaced

`internal/migrate/sources/biztalk/schemas.go` — everything a message-shape feature would want (format, namespace, root element, kind) is parsed into a *plugin-private* struct that never leaves the plugin:

	PropertyByName map[string]int // promoted property name → index into Artifacts

And the public record (`internal/migrate/inventory.go`) is intentionally narrow:

```go
// SchemaArtifact is the inventory-visible record for one source schema
// file. Kept deliberately narrow: id (stable reference), Location (path
// the matcher / agent reads), optional PromotedProperties (filter-routing
// reference), optional LineCount (Deserializer model-strategy input).
//
// Format/namespace/root-element/kind details are parsed by source
// plugins for their own internal indexing but are intentionally NOT
// surfaced — every downstream consumer that needed them in 0.3 has
// since switched to per-flow signals (PipelineRefs, InputSchemaRef,
// OutputSchemaRef, transport-normalized gaps).
type SchemaArtifact struct {
	ID                 string   `json:"id"`
	Location           string   `json:"location"`
	PromotedProperties []string `json:"promoted_properties,omitempty"`
	LineCount          int      `json:"line_count,omitempty"`
}
```

**So: `format` (`xml`/`flat-file`), `kind` (`message`/`property`/`envelope`), target namespace and root element ARE computed today — they are just dropped at the inventory boundary.** Re-exposing them is a one-line change per field.

Classification logic worth knowing:
- `classifySchemaFormat(body)` — byte-probe: `schemas.microsoft.com/BizTalk/2003` + (`groupInfo` | `recordInfo`) ⇒ `flat-file`, else `xml`.
- `classifySchema(parsed)` — reads `&lt;b:schemaInfo schema_type="property|envelope"/&gt;`; absent ⇒ `message`. Property schemas put every top-level `&lt;xs:element&gt;` into `promoted_properties[]` and suppress `root_element`.
- Encoding-aware: `toUTF8` / `decodeUTF16` handle BizTalk's UTF-16-BOM XSDs; failures become `schema-parse-failure` gaps.
- `xsdSchema` parses only `targetNamespace`, annotations, top-level element names — the **XSD body is never lifted**, only a `location` pointer.

Message *type* survives only indirectly, as a filter clause value:

```json

```

Fixed five-step plan, always emitted in this order for `kind=blueprint` (`buildPipelineSteps`): **Deserializer, Extractor, Validator, Transformer, Serializer**.

Pattern vocabulary — **this is the only per-step "message format" signal that exists today**:

```go
PatternPassThrough            = "pass-through"
PatternXMLStreamDeserialize   = "xml-stream-through-deserialize"
PatternXMLStreamSerialize     = "xml-stream-through-serialize"
PatternFlatfileDeserialize    = "flatfile-deserialize"
PatternFlatfileSerialize      = "flatfile-serialize"
PatternXSLCompiledTransformEm = "xsl-compiled-transform-embedded"
```

Derivation:
- `buildDeserializerStep` — `source_refs = [inventory.schemas[input_schema_ref].id]`; pattern = `flatfile-deserialize` if `flowUsesFlatFile(receive)` (i.e. a *receive* pipeline in the flow's own `pipeline_refs` has a stage component containing `ffdasmcomp`), else `xml-stream-through-deserialize` + a `decision_hint` from the schema's `line_count` (threshold 2000 lines ⇒ `stream-through`).
- `buildSerializerStep` — mirror, on `output_schema_ref` and `ffasmcomp`.
- `buildValidatorStep` — `source_refs = flow.pipeline_refs`, `linked_gap` = first `pipeline-custom-component[-missing-source]` gap touching them. Pattern always `pass-through`; no XSD validation is ever derived.
- `buildTransformerStep` — `pass-through` unless a transformation's language is `xsl`/`xslt`.
- `MatchInventory` copies transports **verbatim** onto `trigger` / `destinations[]` and emits one low-severity `transport-normalized` gap per non-`FILE` transport.

## 4. How connectors are modelled (current branch)

Pipeline: template value `connector` → `.intropy/scaffold.json` → `sys create` assembles → C# codegen.

1. **`int create`** (`cmd/intropy/int_create.go`) — no connector flag; it arrives as a generic template value (`--set connector=…`). `internal/template/scaffold.go` records it in `Scaffold.Values` (a bare `map[string]any`), alongside label-derived `Role`, `BlockKind` (`extractor`/`loader`), `DataFlow` (`in`/`out`).

2. **`sys create`** (`internal/system/assemble.go`) reads the value by name:

Dedup: one connector per component (duplicate ⇒ error). Model (`internal/system/model.go`):

**Answer to your question: no.** A connector today is a *name* plus (at codegen time) an unconditional `Transport.File(./test/&lt;name&gt;)`. 	ExternalSystem string    `json:"externalSystem,omitempty"`

## 1. Internal messages: data model

### Recommendation: a top-level `contracts[]` lookup table in the topology doc, in a simple native shape. Not AsyncAPI, not JSON Schema.

The topology doc already has exactly this pattern: `topics[]` and `connectors[]` are lookup tables that inline references resolve against, and `Topic.Contract` is already the join key (the full CLR type name). `contracts[]` is the third table, keyed by that same name. No apiVersion bump — the field is additive, `encoding/json` ignores unknown fields in old CLIs, and old hosts that don't emit it degrade to today's name-only display.

**Why not AsyncAPI:** it's a document *about* channels/servers/operations — the topology doc already is that document, natively. Generating AsyncAPI in the .NET verb means the dashboard parses AsyncAPI back into render data, a round-trip through a foreign vocabulary for zero v1 benefit. **Why not JSON Schema:** C# event records occupy a tiny structural subset (records, primitives, collections, nullability). Rendering arbitrary JSON Schema well (`$ref`, `oneOf`, `allOf`) is far more frontend work than the subset warrants, and "deterministic over complexity" favors a shape the dashboard renders with a plain table. JSON Schema is also derivable later from the native shape if a consumer needs it.

# Contract data model for topology.intropy.io/v1

## 0. The one organizing decision

The topology doc already has a pattern: **top-level lookup tables that inline refs resolve against** (`topics[]`, `connectors[]`). Contracts become the third lookup table: a top-level `contracts[]` registry, keyed by name. This is the move we won't regret because:

- `Topic.contract` **already holds the registry key** ("Contracts.Order"). Making `contracts[]` a table keyed by that exact string means the topic shape doesn't change at all — the existing string field silently becomes a resolvable ref. Zero migration for topics.
- The future `apis[]`/`provides`/`consumes` sockets reference the same table with the same string-ref convention.
- External connector message descriptions live in the same table with a `kind` discriminator, so the dashboard renders "what flows on this edge" through one code path for topic edges and connector edges.

One registry, two kinds of entry:

| `kind` | What it is | Produced by | Has `schema` | Has `description` |
|---|---|---|---|---|
| `event` | CLR record on a pub/sub topic | graph verb (reflection) | yes (JSON Schema) | no |
| `document` | external payload with no spec | authored sidecar file, merged by CLI | no | yes |

Deliberately **not** unified into one fake super-schema: an `event` is generated truth (the serializer's own metadata), a `document` is human documentation. Same registry, different honesty guarantees, and the model says which is which via `kind` + `provenance`.

## 1. Contract identity, schema, fingerprint

**Identity.** `name` is the registry key, unique within the doc. For events it is the fully-qualified CLR name (`Contracts.Order` — matches what `TopologyMaterializer.AccumulateTopic` already emits via `ContractType.FullName`). For documents it is `&lt;connector&gt;/&lt;message-name&gt;`. `shortName` (`Type.Name`, "Order") is carried explicitly — that is the join key to `.intropy/scaffold.json`'s PascalCase `values.contract`, closing the currently-missing scaffold↔topology join without inventing anything.

**Schema: JSON Schema via the in-box exporter, not NJsonSchema, not a custom field list.**

- .NET 10 ships `System.Text.Json.Schema.JsonSchemaExporter` (`JsonSerializerOptions.GetJsonSchemaAsNode(type)`). Zero new dependencies — this matters because Intropy.Topology and Intropy.Topology.Generation are documented as dependency-free, and NJsonSchema would break that for no gain.
- It reflects the **same serializer metadata that will serialize the message at runtime**, so the schema matches the wire shape by construction (nullability, property naming policy, converters). A hand-rolled field list would be a second reflection implementation that drifts.
- Nested records (`OrderLine` inside `Order`) come out as `$defs` automatically; one registry entry per topic root type.
- Generation site: the graph verb, inside `Intropy.Topology.Generation`. This requires one internal-model change: `TopicResource`/`TopicAccumulator` currently reduce `TopicRef&lt;T&gt;.ContractType` to a string (`/Users/robinhultman/dev/intropy/tooling/intropy-topology/src/Intropy.Topology/Building/TopologyMaterializer.cs:110`). Keep the `Type` on the internal model (`ContractType Type` alongside `ContractTypeName`) so Generation can export the schema. The core model stays dependency-free; only Generation calls the exporter.

**Fingerprint.** `fingerprint: "sha256:&lt;first 16 hex&gt;"` over the *canonicalized* schema JSON (sorted keys, no whitespace, stable `$defs` order). This is the version — no semver, no manual bumping; the fingerprint changes exactly when the shape changes. Cross-system drift detection is then a string comparison: two systems both carrying `Contracts.Order` with different fingerprints = drift, render a warning. Caveat to document: exporter output could vary across .NET SDK versions, so fingerprint comparisons are only meaningful within a workspace built on one SDK — acceptable for a local-first tool, and canonicalization absorbs cosmetic churn.

**CloudEvents envelope.** Envelope metadata is a property of the *topic*, not the contract (the same record could ride two topics under different event types). Today the CE `type` is a compiled constant in scaffolded component code, invisible to topology — that's two sources of truth waiting to disagree. Fix at the declaration site, per the deterministic-over-inference value:

```csharp
public static readonly TopicRef&lt;Order&gt; Orders =
    TopicRef&lt;Order&gt;.Define("pubsub", "orders", eventType: "orderflow.orders.extracted");
```

and the scaffolded component code consumes `Topics.Orders.EventType` instead of its private constant — single declaration, graph verb emits it for free. Topic gains `eventType` and `datacontenttype` (constant `application/json` for now; publishers = CE `source`, already present, don't duplicate). This is a release-2 item because it touches the CLI's golden scaffold templates (`internal/system/create_test.go` byte-exact outputs) and the examples that mirror them verbatim.

## 2. AsyncAPI: honest verdict — no as the model, later as an export

**Do not make AsyncAPI the internal format.** The impedance is real:

- AsyncAPI 3.0's channel/operation/message model maps *tolerably* to pubsub topics (channel=topic, message=contract, send/receive operations=publishers/subscribers), but the **highest-value part of this problem — connectors, flat files over SFTP, EDI — has no AsyncAPI home at all.** There is no file/SFTP binding in the spec; everything would be `x-intropy-*` extensions, i.e., you'd be writing the native model anyway, wearing an AsyncAPI costume.
- An AsyncAPI document is scoped to *one application*; Intropy's doc is scoped to a *system of components*. You'd need one AsyncAPI doc per component plus stitching — a shape mismatch with the existing single-doc-per-system pipeline.
- The dashboard needs custom rendering for connectors/blocks regardless, so the AsyncAPI React component only covers the fraction of the UI that is easiest anyway.
- It's a second format to keep true, violating "the topology doc is the interchange".

**What AsyncAPI is good for:** ecosystem tooling (Backstage AsyncAPI plugin, docs portals, code generators) for the *internal event* subset. So: native model in the topology doc; `intropy topology export --format asyncapi` as a **derived, lossy-by-design export** in release 3, *if and when a concrete consumer exists*. The proposed model makes that export mechanical: `contracts[]` (kind=event) → `components.messages` with JSON Schema payloads, `topics[]` → channels, `eventType` → CE binding. Nothing in the model needs to change later to enable it — which is the test that the model is right.

## 3. External message descriptions (`kind: "document"`)

**Design stance: this is documentation, not enforcement, and the model says so out loud.** The runtime never validates against it (consistent with ValidateStep being business-rules-only); its job is to make a developer opening the dashboard understand "what actually arrives in that folder" without archaeology. Fields are chosen to be checkable-by-eyeball, not machine-validatable — that's why there is no `schema` on documents and no pretend-XSD.

**Authoring: sidecar file, not C#.** `ConnectorRef` is deliberately minimal and prose/samples/column tables don't belong in code constants. Sidecar files live next to the declaration site: `&lt;SystemHost&gt;/messages/&lt;connector&gt;.&lt;direction&gt;.&lt;name&gt;.message.json`.

**Transport into the doc: merged by the CLI, not the graph verb.** The graph verb is pure reflection over the assembly with no reliable cwd (`internal/dashboard/topology.go` runs it via `dotnet run --project`); teaching it file I/O is fragile. The CLI already owns the system directory (`Entry.Path`) — `hostGraphProvider` reads `messages/*.message.json`, appends `kind:document` entries to `contracts[]`, and attaches refs to the named connector. This does not violate "the CLI never derives a topology": nothing is inferred — the sidecar is a declared artifact, and a sidecar naming an unknown connector/direction is surfaced in `errors[]`, not guessed around. It also positions the BizTalk branch perfectly: its XSD parser (format, delimiters from `b:recordInfo`, root element) becomes a *bootstrap generator of sidecar files* (`provenance.source: "imported-biztalk-xsd"`), not a runtime dependency.

**Sidecar format** (own apiVersion so it can evolve independently):

```json
{
  "apiVersion": "message.intropy.io/v1",
  "kind": "MessageDescription",
  "name": "pim-order-file",
  "connector": "order-extractor-source",
  "direction": "in",
  "summary": "Nightly order export pushed by PIM.",
  "format": "csv",
  "encoding": "iso-8859-1",
  "delimiters": { "field": ";", "record": "\r\n" },
  "hasHeader": true,
  "filePattern": "ORDERS_*.csv",
  "frequency": "nightly ~02:00 CET, pushed by PIM batch job",
  "fields": [
    { "name": "ORDER_ID",  "position": 1, "type": "string",  "required": true,  "notes": "PIM order key, zero-padded 10" },
    { "name": "CUST_NO",   "position": 2, "type": "string",  "required": true },
    { "name": "ORDER_DATE","position": 3, "type": "date",    "required": true,  "notes": "yyyyMMdd" },
    { "name": "QTY",       "position": 5, "type": "integer", "required": false, "notes": "empty means 1 (per PIM ops)" }
  ],
  "sample": { "inline": "1000000042;C1234;20260725;SKU-1;3", "redacted": true },
  "contact": "PIM operations — anna.b@customer.example (source of truth)",
  "notes": "PIM occasionally re-sends the whole file after a failed run; ORDER_ID is the dedupe key.",
  "provenance": { "source": "authored", "lastReviewed": "2026-07-26" }
}
```

Design notes, opinionated:
- `format` is a small open enum: `csv | flat-file | xml | json | edifact | x12 | binary | other`. `type` on fields is deliberately loose (`string|integer|decimal|date|boolean|other`) — "type-ish", because that's all anyone actually knows about a PIM export.
- `sample.inline` only, one-to-few lines, with a **required** `redacted` boolean so the author must assert they thought about PII before the dashboard displays it. No file refs in v1 — a path into someone's SFTP dump is a stale link and a data-leak vector; inline-snippet-or-nothing keeps it honest and portable.
- `frequency` is prose, not cron — the schedule belongs to the *external* system; pretending precision we don't have is the fake-schema trap in another field.
- `provenance.lastReviewed` is the staleness mechanism: the dashboard renders a "reviewed N months ago" badge. That plus `contact` is the entire honesty story — social, not mechanical, stated explicitly in the model docs.

## 5. Cross-system view: design now (two fields), build later

The design cost is exactly `fingerprint` + stable `name` — both already in the model above for their own reasons (drift detection, registry identity). The workspace-level join is pure dashboard logic over data the CLI already aggregates (`TopologyReport.topologies[]`): group `contracts[]` entries by `name` across entries; equal fingerprints → "same contract flows through systems A and B" (a genuinely great overview affordance); unequal → drift warning. **Do not** build a cross-system UI in v1, and do not add any cross-system structure to the per-system doc (it must stay a statement about one system). The model is ready; the feature is a release-2/3 pull.

## 6. Migration &amp; versioning

- **Stay on `topology.intropy.io/v1`. Purely additive.** Go's `encoding/json` ignores unknown fields, so old CLI + new host is safe; new CLI + old host just sees no `contracts[]` and the UI falls back to rendering `Topic.contract` as a bare string (today's behavior). The strict apiVersion gate in `topology.Decode` is untouched. Reserve a v2 bump for genuinely breaking shape changes; this isn't one.
- `messages[]` on connector and `eventType`/`datacontenttype` on topic: additive, `omitempty` throughout.
- The C# `EndToEndTests` byte-exact snapshot changes deliberately (documented workflow) — internal model gains the retained `Type`, graph doc gains `contracts`.
- The sidecar format versions independently (`message.intropy.io/v1`) with the same strict-gate policy as the topology decoder.
- Contract *entries* have no version field: the fingerprint is the version.
