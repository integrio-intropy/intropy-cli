## 2. How relationships/edges are derived today

Topology is **not modeled server-side at all**. The Go API emits a flat list of integrations, each with its own parsed Dapr components and pipeline-step filenames. There is no server-side notion of nodes/edges, no cross-integration linking, no code scanning, no publish/subscribe topic graph.

All edges are **synthesized in the browser** by `buildGraph` in `/Users/robinhultman/dev/intropy/tooling/intropy-cli/web/src/components/FlowView.tsx:255-414`, using heuristics:
- **Grouping into a "system"**: integrations are grouped by `domain/system` folder pair (`systemKey`, FlowView.tsx:115-117) — i.e. purely by directory layout, not by any declared membership. Root-level integrations fall into a `__workspace__` pseudo-system.
- **Shared infra nodes** (pubsub/state): deduped across the system by `category:name` (FlowView.tsx:265-277). An edge is drawn from each integration to any pubsub/state component it declares (FlowView.tsx:397-411).
- **External systems** (bindings): rendered outside the boundary, per-integration. Direction decides side/arrows: `input` → source on the left feeding the integration; anything undeclared → sink on the right; `input,output` → bidirectional arrows (FlowView.tsx:345-395).
- **Pub/sub edges are NOT topic-aware**: there is no matching of a publisher's topic to a subscriber's topic. Two integrations "connect" only transitively by both pointing at the same named pubsub *component*, not by an actual publish→subscribe topic flow. A true pub/sub flow edge (producer topic → consumer topic) does not exist.

So relationships are inferred from (a) filesystem nesting (system grouping) and (b) each integration's own Dapr component files — never from code, config beyond Dapr YAML, or a declared topology.

Key guesses/hardcoding gaps:
- **`TEMPLATE_DATA_FLOW` hardcoded map** (FlowView.tsx:68-73): `extractor→in, loader→out, transactional→both, aggregator→internal`. This is a fallback direction-by-template-name for scaffolds predating the `dataFlow` field. New templates are expected to declare `intropy.dev/data-flow` instead (see §4).
- **Disk-vs-cloud external icon** guessed by regex on the component type string: `/localstorage|localfile|disk|file/i` (FlowView.tsx:466).
- Undeclared binding direction is rendered as a sink (documented as "unknown is not guessed" but visually defaults to sink).
- System membership is inferred from folder depth only; there is no explicit system manifest.

The only persisted topology signal is the per-integration `dataFlow` (`in|out|both|internal`) from the `intropy.dev/data-flow` template label, with a hardcoded `TEMPLATE_DATA_FLOW` name map as fallback.
