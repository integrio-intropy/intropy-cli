## 2. What the xregistry client does

**Exactly one endpoint: `GET /export`.** There is no per-entity path, no filtering, no pagination, no inlining query params — `client.go:11-16` states the registry declares those out of scope, so the client "sends only GET /export — no query params it did not see advertised."

```go
func New(baseURL string, opts ...Option) (*Client, error)   // client.go:64  — must be absolute
func WithHTTPClient(c *http.Client) Option                  // client.go:53
func WithUserAgent(ua string) Option                        // client.go:58
func (c *Client) BaseURL() string                           // client.go:81
func (c *Client) Export(ctx context.Context) (*Export, error) // client.go:143
func (c *Client) Resolve(ctx, ref string) (*ResolvedMessage, error) // resolve.go:195
```
- 15 s default timeout (`client.go:41`), 64 MiB body cap (`client.go:117`), `Accept: application/json`
- non-200 → error naming the URL plus a condensed `{code, detail}` error document (`client.go:105-138`)

**Data model (`types.go`) — the doc view of xRegistry 1.0-rc2x:**
```go
type Export struct { SpecVersion, RegistryID string
    MessageGroups map[string]MessageGroup    // "messagegroups"
    Endpoints     map[string]Endpoint        // "endpoints"
    SchemaGroups  map[string]SchemaGroup }   // "schemagroups"

type MessageGroup struct { ID, Name string; Messages map[string]Message }
type Message      struct { ID string; Versions map[string]*MessageVersion }
type MessageVersion struct { VersionID string; IsDefault bool
    Envelope, DataSchemaFormat, DataSchemaXID, DataContentType string
    EnvelopeMetadata map[string]CEAttribute }
type CEAttribute  struct { Value any; Type string; Required bool; Description string }
type Endpoint     struct { ID, Name, Channel string; Usage, MessageGroups []string }
type SchemaGroup  struct { ID, Name string; Schemas map[string]Schema }
type Schema       struct { ID, Format string; Versions map[string]Version }
type Version      struct { VersionID, XID string; IsDefault bool }
```
Key modelling note (`types.go:8-13`): messages are `maxversions: 1`, so every definition attribute lives on the single implicit version, never on the resource — hence `Message.DefaultMessage()` (`client.go:153`, sorted-id fallback so nothing depends on map order).

**Resolution (`resolve.go`) — what it returns:**
```go
type Channel struct { Pubsub, Topic, Endpoint string }         // resolve.go:13
type ResolvedMessage struct { Message, Type, Group string
    Channels []Channel; DataSchema, DataSchemaURL string }     // resolve.go:22
func ResolveMessage(doc *Export, ref string) (*ResolvedMessage, error)     // :51
func (r *ResolvedMessage) SubscribeChannel() (Channel, error)              // :93
func FindMessage(doc *Export, ref string) (*Message, *MessageGroup, error) // :108
func SplitChannel(channel string) (pubsub, topic string, err error)        // :216
func DefaultSchemaVersionXID(doc *Export, xid string) (string, error)      // :228
```
The join xRegistry does not provide (`client.go:11-14`): message → group → endpoints where `usage` contains `"producer"` and `messagegroups` contains `/messagegroups/&lt;gid&gt;` → split `&lt;pubsub&gt;/&lt;topic&gt;` (`producerChannels`, `resolve.go:166-189`, sorted for determinism). CloudEvents type comes from `envelopemetadata["type"].value` (`resolve.go:65-69`). Schema pin: `dataschemaxid` → the version with `isdefault` → its `xid`, made absolute against the base URL only in `Client.Resolve` (`resolve.go:204-208`) — `ResolveMessage` alone keeps the root-relative xid.

Refs accepted: bare message id (unique across groups, else an ambiguity error listing group xids) or full `/messagegroups/&lt;gid&gt;/messages/&lt;mid&gt;` (`resolve.go:112-149`).

**Typed errors (`errors.go`):** `MessageNotFoundError`, `NoProducerError{Group}`, `AmbiguousProducerError{Ref, Channels}` (message names endpoint + channel per candidate, `errors.go:35-48`), `ChannelFormatError{Endpoint, Channel}` (unwrappable), `SchemaNotFoundError{XID}`, `NoDefaultVersionError{Ref, Group}`.

- **Two schema fields, both references only:**

- The only actual JSON Schema machinery in the repo is unrelated: `internal/template/values.go:13,362` validates *template parameters* with `santhosh-tekuri/jsonschema/v5`, and `web/src/api.ts:353-380` + `components/ContractDetail.tsx`/`FlowDetail.tsx:201-290` render the **host-emitted `Contract.schema`** from the topology record (the .NET contract registry), not a registry message schema.

## Implications for the feature you're planning

1. **The contract body must be generated on the CLI side and handed to the template as structured data.** The template-side `.cs.tmpl` would `range` over a field list. The mechanism already exists and is named: a new reserved key via `InjectReserved` (`internal/template/reserved.go:43`), injected *after* `ResolveWith` returns.
2. **The dependency edge is the blocker.** `Contracts/` is rendered by `renderDependency` (`internal/template/dependencies.go:117`), whose values come from `renderDependencyValues` (`:167`) — a `map[string]string` of rendered Go-template expressions. Structured field data cannot cross that edge today; `Resolve` is also called there with a nil prompter (`:126`). Either extend the dependency-values plumbing to carry a reserved block, or inject the reserved key into the dependency render explicitly.
3. **Schema fetching is net-new.** `xregistry.Client` only does `GET /export` (`client.go:143`), and `types.Schema` (`types.go:85`) carries no document. You already get an absolute, immutable pin in `ResolvedMessage.DataSchemaURL` (`resolve.go:204-208`) and it's recorded in the scaffold blocks — that's the input.
4. **The record is forward-compatible.** `Scaffold` is additive-only with no version bump needed (`scaffold.go:12-15`), so recording the generated field set / schema digest is cheap. Three write sites though (`create.go:164`, `prepare.go:126`, `dependencies.go:143`).
5. **You'd be writing new type-mapping and C#-identifier code from scratch** — nothing exists to extend. PascalCase is currently only a regex `pattern` in template manifests, not a transform.

## Summary for the generation design

- **Physical target**: one file per record at `&lt;system&gt;/Contracts/&lt;Contract&gt;.cs`, namespace `Contracts`, flat `net10.0` class library with no package references. Nested types (`$defs`) go as sibling records in the same namespace — `OrderLine.cs` is the existing precedent.
- **Name source**: the `contract` param, currently required and hand-typed (`extractor/template.yaml:50-54`), and echoed into the `publishes`/`subscribe` block. The schema's `title` is the natural derivation (`"Export Event"` → `ExportEvent`, which is already what the fixture passes by hand).
- **The seam already exists**: `empty: true` renders `public record X();` — an intentional placeholder — and `schemaUrl` already carries the pin into the render context, with the template comments explicitly reserving codegen for "an external tool".
- **Cheapest data path**: `/export` already inlines every schema document; the CLI already fetches it and just needs a `schema` field on `internal/xregistry/types.go:93`. Falling back to `GET &lt;dataschemaurl&gt;` works too and returns `application/schema+json` directly.
- **Two constraints to respect**: `$defs`/`$ref` and `additionalProperties: false` in the real seed schemas; and `contractNamespace` in `system-host/skeleton/Topics.cs.tmpl:19-28`, which already anticipates contracts living in a sub-namespace of the contracts project.</result>
