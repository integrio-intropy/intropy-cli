# 1. AGENTS.md — the verb contract

`/Users/robinhultman/dev/intropy/tooling/intropy-cli/AGENTS.md` (162 lines) is a **writing-style + verb-set contract**, not an architecture doc. Sections: code comments, cobra help text, flag descriptions (constants in `cmd/intropy/flagtext.go`), runtime output (stdout = results, stderr = everything else), voice, errors, vocabulary, and — the load-bearing part for a portal — **Command verbs** (lines 104–154).

The canonical verb set, grouped by effect on the world:

| Group | Verb | Contract |
|---|---|---|
| Read-only (exit 0 even on disagreement, never write git, never sync) | `list` | enumerates a collection; never prints one item's details |
| | `show` | details of exactly one thing; never enumerates |
| | `status` | one component across **every** environment, one row each, plus whether rows agree |
| | `diff` | the rendered change a `sync` would apply; both sides are committed revisions |
| Local project state (may write files, never push) | `create` | makes something new from a template or scaffolded parts |
| | `add` | attaches something that already exists elsewhere (pulled, not generated) |
| | `update` | reconciles an installed thing against the ref its source pins; never changes the pin |
| | `init` | scaffolds the GitOps tree a system needs, as a **branch pushed for review**; one per system |
| Move / publish | `publish` | immutable artifact to an OCI registry; edits are new versions |
| | `pin` | one component's image digest into one environment's overlay |
| | `promote` | copies digests one env runs into the next in the promotion graph |
| | `sync` | applies an env's pending change through ArgoCD; never decides what the change is |

Explicit anti-rule: do not import kubectl's `get`/`describe` split — `int describe` was retired. `cmd/intropy/int_describe.go` remains only as a deprecation shim. New verbs need a written reason in this file.

Vocabulary rules worth mirroring in a portal UI: **image digest** (never "bits"/"artifacts"), **environment** in prose (`--env` only when naming the flag), `-&gt;` for a transition, ` @ ` for a pin, 7-char short SHAs.

# Concept: **The Exchange** — a fact-ledger catalogue in Intropy's own language

## 1. Pitch

Backstage is a catalogue you *author*: YAML files describing generic Components so a portal can render them. The Exchange is a catalogue you *cannot author*: every entry is a fact the `intropy` CLI already emitted — scaffold records, `topology.intropy.io/v1` graphs, OCI release manifests, `deploy status` results — ingested verbatim with provenance ("as reported by `deploy status`, commit `a1b2c3d`, 14:02"). Its kinds are Intropy's kinds (System, Component, Contract, Topic, Connector, Release, Environment, Domain), and its center of gravity is the one thing no generic catalogue has: the **contract fingerprint**, a hash that makes "these two systems exchange the same shape" a computable fact. Where Backstage answers "what services exist?", The Exchange answers the architect's real questions: *who else speaks this shape, what breaks if I change it, and does prod run the bits staging tested?*

## 2. Core model

**Unit of truth: the fact.** A fact is one versioned JSON document the CLI or a system host emitted, stored unmodified plus an envelope: `{urn, kind, observedAt, source (command + version + commit + CI run), payload}`. The portal never re-derives; it joins. This extends the codebase tenet — the portal cannot claim what the command line would not — into an ingestion rule.

**Store: a git-backed fact ledger, no database.** A per-customer "catalogue repo": `facts/&lt;customer&gt;/&lt;domain&gt;/&lt;system&gt;/&lt;component&gt;/&lt;kind&gt;/&lt;observedAt&gt;.json`, plus `latest.json` pointers. The portal serves from an in-memory index rebuilt on start; history is `git log`. Small team, greppable truth, trivially backed up, and the fleet story is just cloning N customer ledgers into one Integrio index.

**Population: push from where facts are born, pull for reconciliation.** CI pipelines run the verbs they already run (`release create`, topology `graph`, `deploy status --output json`) and POST the JSON to the portal's ingest endpoint (or run `intropy facts push`). A background reconciler pulls the GitOps repo, OCI registries, and ArgoCD (via the CLI in agent mode) so a quiet CI never means a stale portal — but pull results carry the same provenance envelope, never a portal-invented claim.

**Identity:** URNs mirror the GitOps tree with customer as the leading segment from day one: `intropy://acme/logistics/erp-orders/order-extract`. Environments: `intropy://acme/~env/prod`. Contracts have two identities: the *name* (an alias, per system) and the *fingerprint* (the shape, global). Cross-system joins always go through fingerprint; names collide, shapes don't. Fleet aggregation later = merge indexes; URNs already disambiguate.

## 3. Information architecture

| Surface | Question it answers | For |
|---|---|---|
| **Estate** (home) | What do we run, where, and does it agree? Domains → systems grid with release currency, `consistent` flags, pending gates. Summaries rendered as served. | Architect, ops rotation |
| **Contract Exchange** | Who publishes/consumes this shape, across systems? Which environments run an older fingerprint? Impact radius of a change. | Architect (the signature screen) |
| **System** | One system's declared topology, components, contracts, connectors, release history, environment ladder — the org-persistent sibling of the dashboard's system view, built from ingested facts, not a workspace. | Everyone |
| **Connector directory** | What touches SAP / the partner SFTP? External systems as first-class entries: transports per environment, `messages/*.md` payload docs, contacts, every component wired to them. | Architect, ops, onboarding |
| **Ledger** | What changed, when, by whom? Chronological releases, pins, promotes, syncs across the estate, with `changes[]` and `changeBasis`. | Ops rotation, audits |
| **Knowledge** | How do I think about / operate this? The OKF catalog rendered *contextually*: a doc's `sources[]`/`commands[]` frontmatter binds it to entities, so the deployment-troubleshooting playbook appears on any environment row whose sync failed. | Developers, agents |

## 4. Runtime stance

The line is the **fact boundary**: deployment *state* is in (pins, sync/health status, consistency, pending gates — all already CLI-emitted facts); *telemetry* is out (rates, latencies, traces render in the monitoring tool, never in the portal). Ops-on-rotation gets exactly three runtime affordances: the Estate consistency board, a pending-gates list, and per-entity deep links into monitoring. The portal also never *acts*: it renders the exact command to run (`intropy deploy promote order-extract --env prod`) rather than a button. That keeps identity crisp — it is the estate's memory, not a control plane.

## 5. Tight integrations

**Diagramming — diagrams as bound views.** Shapes on a canvas bind to catalogue URNs. Layout, grouping, and annotations are the architect's; edges, labels, contract names, and status chips **hydrate live** from the portal's graph API. Two dream behaviors: (a) *conformance diffing* — the architect draws a proposed component or edge as an unbound shape; the portal overlays "designed but not built / built but not drawn," turning the diagram into an architecture gate; (b) *staleness detection* — a binding whose URN vanished flags the diagram, so documentation can no longer silently rot. Diagrams embed back into System pages as live frames.

**Monitoring — the portal exports identity, monitoring exports attention.** Outbound: every ingested deploy fact posts an annotation ("2.4.0 pinned to prod") onto the relevant dashboards; the URN taxonomy becomes monitoring's label scheme; the portal *generates* each system's baseline dashboard from topology (one panel per topic, per connector, per DLQ). Inbound: alerts carry URNs, so entities wear a single "attention" chip that deep-links to the firing alert — the portal knows *that* something is wrong and *who* it is, never *how much*.

## 6. Relationship to dashboard and CLI

CLI: the only writer and the only actor. Dashboard: *my workspace, now* — live disk state, single developer, mutable. Portal: *our estate, remembered* — ingested facts, multi-user, historical, cross-system. The dashboard reads a checkout; the portal reads the ledger. Shared TypeScript fact types keep the two renderings literally the same shapes (api.ts already mirrors the Go contracts).

## 7. Why it wins / where it's weak

**Wins:** zero authoring burden (the anti-`catalog-info.yaml`); the fingerprint join answers questions Backstage structurally cannot; provenance-everywhere makes it trustworthy in the exact way the CLI already is; git-backed store + one Go binary = a small team can own it; customer dimension is native, so the Integrio fleet view is a merge, not a migration.

**Weak:** freshness depends on CI pushing facts — a customer with lazy pipelines gets a stale portal (mitigated, not solved, by the reconciler); read-only can feel passive next to portals with actions; no plugin ecosystem — every new need is portal code; git as a store is coarse for rich queries at fleet scale and may eventually force an index sidecar; the knowledge/entity binding is only as good as OKF frontmatter discipline.

## 1. Pitch

Enterprise integration is not a list of services; it is literally a graph — data leaves SAP, crosses three system boundaries, and lands in a warehouse. Page-first portals (Backstage) shred that graph into entity pages and force the architect to rebuild the picture in their head. Atlas inverts it: one continuously true, machine-fed architecture map is the front door, and every question — "what talks to what?", "what runs in prod?", "where did tonight's file stop?" — is answered by pointing at the same picture at a different zoom level with a different overlay. The domain already earns this: topology is host-declared fact (`topology.intropy.io/v1`), contract fingerprints are cryptographic join keys across systems, and deploy state is versioned CLI JSON. Atlas never invents wiring; it only draws what was declared or provably joined.

## 2. Core model

**Four semantic layers, one graph store:**

- **L0 Landscape** — systems (from each ingested topology's `system`), external systems (union of `connectors[].externalSystem` across all systems), domains as spatial regions.
- **L1 System** — the exact graph FlowView renders today: components, topics, connectors inside a boundary.
- **L2 Component** — pipeline steps, contract surfaces (provides/consumes), connector detail, deployment ladder.
- **L3 Contract** — schema field tree, fingerprint, and every usage site estate-wide.

**Cross-system edge derivation (the portal's one genuinely new computation), with explicit provenance types:**

1. **Shared external system** (`externalSystem` name equality): System A's connector `out` to "SAP" and System B's connector `in` from "SAP" collapse onto one shared external-system node. This is fact-level — both declared it — but rendered as a *mediated path* A → SAP → B, never a direct A→B edge.
2. **Fingerprint join** (`Contract.Fingerprint` equality): a contract published outward by A whose fingerprint equals one consumed by B yields a *derived edge*, drawn dashed and labeled "same shape". Equal fingerprints mean equal shapes, not proven data flow — so derived edges are visually distinct and **confirmable**: an architect promotes a derived edge to a confirmed one, which is stored as an intent annotation, not injected into topology.

**Intent vs reality — GitOps for architecture:** Atlas holds two graphs. *Reality* is the aggregation of ingested topology + deploy facts (immutable, machine-owned). *Intent* is architect-owned: imported diagrams, confirmed edges, planned/ghost systems, ADR links. A reconciler diffs them continuously into drift states: **undocumented** (in reality, not intent), **planned** (in intent, not built), **mismatched** (direction/contract/fingerprint changed). Drift is a first-class map badge, not a report.

## 3. Information architecture

| Zoom | Shows | Question answered | For |
|---|---|---|---|
| Landscape | System boxes, external systems, mediated/derived/confirmed flows, drift badges, env-health rollup dots | "What talks to what across the estate? What's undocumented?" | Architect, leadership |
| System | Components, topics, connectors (FlowView's picture) with cross-boundary edges stubbed to neighbors | "How does this system work, and who feeds it?" | Developer, architect |
| Component | Pipeline steps, deployment ladder, contract in/out, telemetry sparkline | "What does this do, which release runs where, is it healthy?" | Dev wearing ops hat |
| Contract | Schema tree, fingerprint, all publishers/consumers estate-wide | "Who breaks if this field changes?" | Architect |

The **sidebar catalogue** is the map's index, never a destination: search/tree results *fly the camera* to the node and open its inspector panel. List-shaped queries ("everything on release 1.4", "everything touching contract X") become **highlight sets** — matching nodes glow, everything else dims — rather than table pages.

## 4. Runtime/architecture stance

Three exclusive **overlay modes** on the identical geometry:

- **Design** — intent + reality + drift. No runtime at all.
- **Deploy** — pick an environment: release/digest per component, sync/health from ArgoCD, promotion deltas ("staging is 2 releases ahead") as edge annotations on the ladder.
- **Runtime** — per environment: flow rate as edge thickness/animation, error-rate heat on nodes, last-run recency, dead-letter depth badges, plus a **time scrubber** replaying the last 24h/7d of overlay state.

**The line:** the map carries *aggregates only* — rates, counts, statuses, recency. Never logs, traces, or message bodies. Atlas answers "where is it broken and what's downstream of the break?"; one click deep-links into the monitoring tool pre-scoped to (component, environment, time window) for forensics. If a feature needs a log line, it belongs to the monitoring tool.

## 5. Tool integrations

**Diagramming (existential):** Phase 1 — *import as intent*: existing diagrams are bound shape-by-shape to Atlas node IDs (one-time manual binding, name-matching assisted); thereafter the diagram *is* the intent layer and drift is computed against it on every topology ingest. Drift results push back as markers/comments on the diagram ("this connector no longer exists"). Phase 2 — *embed flips direction*: the diagramming tool embeds live Atlas views (URL-addressable scope + overlay + time pin), so architecture docs stop rotting; hand-drawing survives only for ghost/planned elements, which round-trip into Atlas as intent nodes. Annotations (notes, decision links) authored in either tool sync both ways via the binding table.

**Monitoring:** requires a labeling convention the deploy pipeline already can guarantee: every metric carries `{env, system, component, topic|connector}` matching topology identifiers. Atlas pulls series via query API: messages/sec per edge, error rate, p95 latency, dead-letter depth, last-success timestamp per component. Anomaly alerts from the monitoring tool arrive as webhook events rendered as map pins on the scrubber timeline; monitoring dashboards get a reciprocal "show on map" link.

## 6. Relationship to dashboard and CLI

The dashboard stays the *single-workspace, local, one-developer* surface (catalog, scaffold context, one system's flow, deploy actions). Atlas is *org-level, read-only, persistent*: CI on each system repo pushes the host's topology record and `deploy status --json` to Atlas's ingest endpoint (same versioned schemas — `internal/topology` and `internal/deploy/result.go` are already the wire contract). Code reuse is direct: extract FlowView's deterministic layout engine and node components (`web/src/components/FlowView.tsx`, ~700 lines, already theme-aware @xyflow/react) into a shared package — Atlas's L1 zoom is FlowView verbatim with a different data source; `web/src/api.ts` types become the ingest schema. Same Go-server-with-embedded-Vite-SPA shape. Customer becomes a future top-level dimension above Landscape (Integrio fleet view = L-1).

## 7. Why it wins / where it's weak

**Wins:** the domain is a graph and fingerprints give provable cross-system joins no generic portal has; drift-as-a-feature finally makes diagrams trustworthy; one spatial memory serves design, deploy, and incident triage; small ingest surface (two existing JSON schemas) keeps it maintainable.

**Weak (honestly):** legibility past ~40 systems demands aggressive domain-clustering and a *persisted stable layout* — the map must be "the same place" every day, so layout anchors are stored, not recomputed. List-shaped questions are second-class (mitigated by highlight sets, but tables are sometimes just better). Diagram binding is manual toil at adoption. Runtime overlay is a permanent scope-creep temptation toward becoming a bad monitoring tool — the aggregates-only line must be policed.

## 8. Mocked v0 skeleton

A single Go binary (`atlas serve --fixtures ./fixtures`) embedding a Vite/React SPA (@xyflow/react), consistent with this repo. Fixtures: five `topology.intropy.io/v1` records sharing two fingerprints and three external systems; per-env deploy-status JSON (dev/staging/prod); a mocked metrics time-series JSON (24h at 5-min resolution); one intent fixture containing a planned system and a deliberately stale connector. Demonstrates: semantic zoom L0→L3 with camera fly-to, the three overlay modes, environment switcher, time scrubber animating edge thickness/error heat, drift badges with an intent-vs-reality diff panel, search-as-highlight. No auth, no real integrations — every API call served from fixtures behind the same handler interfaces real ingest would use.

# Concept: **Chronicle** — the interrogatable ledger

## 1. Pitch

Chronicle is not a site you browse; it is a record you interrogate. Backstage's unit is the entity page — a hand-fed snapshot that is stale the moment you read it. Chronicle's unit is the **fact**: an append-only ledger of domain events derived from sources Intropy already produces (GitOps history with `Deploy-*` trailers, OCI release manifests, topology emissions, ArgoCD). Entity pages still exist, but each one is literally the fold of its facts — which means every page has a time scrubber, every difference has a cause, and every question of the form "what changed / since when / why" has a first-class answer. The same substrate serves humans and agents: the ledger plus the OKF knowledge catalog is one queryable brain.

## 2. Core model

**Fact types and sources** (payload is the CLI-emitted JSON verbatim — never re-derived):

| Fact | Source |
|---|---|
| `release.created` | OCI registry: release manifest (version, source commit, images+digests, changes[], changeBasis) |
| `env.pinned` | GitOps log: commit with `Deploy-Component/Env/Digest/By` trailers |
| `env.promoted` | Same, with `Deploy-Promoted-From` |
| `env.synced` | ArgoCD (webhook/poll): revision, health |
| `gate.pending` / `gate.applied` | GitOps + ArgoCD: manual-sync env has committed-but-unapplied overlay |
| `env.diverged` / `env.converged` | *Derived*: `StatusResult.Consistent` flips (marked derived, carries the in-payload Summary) |
| `contract.changed` | topology.intropy.io/v1 snapshot diff: fingerprint changed |
| `consumer.attached` / `detached` | Fingerprint equality across systems appears/disappears |
| `component.scaffolded` | scaffold.json appears in source repo |
| `gap.opened` / `gap.resolved` | Migration gap records (category, severity, resolution) |
| `monitor.alerted` / `resolved`, `slo.breached` | Monitoring integration (curated; see §4) |
| `knowledge.verified` | OKF catalog entry gains `verified` frontmatter (git history of catalog/) |

**Materialization.** The ledger is a materialized view, not new infrastructure anyone must feed. Per-customer instance: pollers/webhooks fold the durable sources (git log, OCI tags, topology emissions) into an append-only store (SQLite is enough). Fact id = content hash → idempotent re-ingest; the whole ledger is rebuildable from scratch, so it holds no state anyone must protect. Unparseable GitOps commits become `fact.unrecognized` — visible, never silently dropped.

**Identity.** URNs with the customer dimension present from day one: `urn:intropy:&lt;customer&gt;:&lt;domain&gt;:&lt;system&gt;:&lt;component&gt;`, sub-subjects `…:env/&lt;env&gt;`, `…:release/&lt;component&gt;@&lt;version&gt;`, `…:contract/&lt;fingerprint&gt;` (fingerprint is already a cross-system identity — equal fingerprint = same shape). Fleet-wide Integrio aggregation later is a union of ledgers over the same scheme.

**Catalogue as projection.** A System page is `fold(facts where subject ∈ system)`: current pins per env, live contracts, open gaps — with its history one scroll below and an "as of" scrubber (fold up to T). The catalogue requirement is satisfied by construction, and it can never disagree with the timeline because it *is* the timeline, folded. Folds are cached snapshots; the 90% "current state" case never replays history.

## 3. Information architecture

- **The Ledger** (home): filtered timeline (type/system/env/actor), grouped by day, with a per-user **"since you were last here"** cursor. For the on-rotation person: "what changed since I was last on call?" is the default render. Primary persona: ops-hat.
- **Ask**: a question box with **canned interrogatives as the contract** ("why is prod ≠ staging for X?", "who consumes contract F and since when?", "what happened to order flow X last Tuesday?") compiled to ledger queries; free text falls through to the agent (best-effort, clearly labeled). Personas: all.
- **Diff**: `fold(A, t1)` vs `fold(B, t2)` — env-vs-env or then-vs-now — showing not just the delta but the facts that *caused* each difference. Persona: architect, approver at the manual gate.
- **Catalogue**: browsable entity projections with scrubbers. Persona: newcomers, architects.
- **Handover**: everything since cursor, prioritized — prod pins, pending gates, alerts correlated with deploys, unresolved gaps. Persona: rotation change.

## 4. Runtime mixing stance

Rule: **the ledger records state changes, never telemetry.** Alert fired/resolved, SLO breach entered/exited, anomaly *verdict* — discrete, low-cardinality, correlatable to deploys — enter as facts carrying deep links back. Metrics, logs, traces, raw flapping alerts stay in the monitoring tool. Chronicle answers "what changed and why"; monitoring answers "what is happening now". This line is what keeps Chronicle from becoming a second monitoring tool.

## 5. Integrations

**Diagramming.** Diagrams are time-addressable projections: "the architecture as of March" renders the diagramming tool from `fold(topology facts, March)`. Embedded diagrams get a scrubber that replays contract/pin facts; clicking an edge opens the ledger filtered to that contract. Ask can generate scoped diagrams ("everything consuming contract F, annotated with since-when").

**Monitoring.** "Explain this alert": alert fact correlates by URN + window, and Chronicle walks backward — alert → last `env.synced` → pin trailers → release manifest → `changes[]` commits → `Deploy-By`. One click from alert to commit subjects and the human who deployed. Reverse direction: Chronicle pushes deploy markers to monitoring dashboards.

## 6. Agent story

One MCP server exposes (a) ledger tools — `facts(filter)`, `fold(subject, at)`, `diff(a, b)` — and (b) the OKF catalog (concepts/workflows/playbooks with `sources[]`/`commands[]`, as piloted in `catalog/`). The playbook triage table (Symptom | Boundary | Evidence | Safe-next-action) becomes executable: symptom → evidence rows resolve to ledger queries → safe action resolves to a CLI command. Agents may append **derived** facts (`actor: agent`, hypothesis-flagged) — e.g., "alert X correlates with pin Y" — which humans confirm or dismiss. The Ask surface *is* this agent; humans and agents share one substrate.

## 7. Division of labor

CLI: the only writer of domain state and emitter of canonical facts. Dashboard (`intropy dashboard`): the individual's now-view of one workspace. Chronicle: org-level memory — cross-system, cross-env, multi-user, historical. Chronicle never mutates: when action is needed it renders the command in backticks (house style) and you take it to the CLI.

## 8. Why it wins / where it's weak

**Wins:** zero new write paths (rebuildable from durable sources); catalogue can't rot (it's a fold); the on-call/handover story is unmatched; fingerprint-based consumer lineage ("who, since when") is a question Backstage structurally cannot answer; agent-first for free.

**Weak:** a timeline is an intimidating front door for newcomers (mitigation: Catalogue + canned Ask questions as entry points); correctness depends on trailer discipline and connector coverage; temporal queries are the pitch but current-state is the daily use, so fold caching must be excellent; free-text Ask risks over-promising — canned questions are the contract; "gap" and monitoring connectors need per-customer adapters.

## 9. Mocked v0 scope

Go binary `chronicle serve` embedding a Vite/React SPA (same pattern as `web/embed.go` + `internal/dashboard`). Fixtures: ~120 hand-written facts (JSON under `fixtures/`) for 3 systems × 3 envs telling **one incident arc**: scaffold → `release.created` 1.4.0 → pin dev → promote staging → `contract.changed` → `monitor.alerted` staging → `gap.opened` → fix release → promote → `monitor.resolved` → `gate.pending` prod. Surfaces: Ledger with filters + since-cursor; one System fold page with as-of scrubber; staging-vs-prod diff; Ask with 4 canned questions wired to real queries (free text stubbed); the "explain this alert" trace-back panel. One arc demonstrates every claim in this document.
