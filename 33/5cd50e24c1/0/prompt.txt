## Summary: existing manifest/config surface in intropy-cli

**Key upfront finding:** The CLI itself only ever writes ONE machine-readable per-project file — `.intropy/scaffold.json`. Everything else (AGENTS.md, Taskfile, Dapr components, C# source, README) is rendered from a *remote* template skeleton (fetched from `integrio-intropy/intropy-templates`), not emitted by CLI Go code. There is no `template.yaml` in this repo. There is currently **no** `topology.json`, no `dapr.yaml` multi-app run file, and no cron/workload concept anywhere in generated output.

---

### 1. What `int create` generates + scaffold.json structure

`Create()` at `/Users/robinhultman/dev/intropy/tooling/intropy-cli/internal/template/create.go` (lines 66-110) does: resolve GitHub release → download template tarball → render `&lt;template&gt;/skeleton/` into `--output` dir → write `.intropy/scaffold.json`. Optionally writes a `CreateResult` JSON only when `--output-json` is passed (lines 40-47; carries `outputDir`, not persisted in project).

The scaffold record struct is in `/Users/robinhultman/dev/intropy/tooling/intropy-cli/internal/template/scaffold.go` (lines 32-44):

```go
type Scaffold struct {
	SchemaVersion int    `json:"schemaVersion"` // ScaffoldSchemaVersion = 1
	Template      string `json:"template"`      // dir name in template library repo
	Owner         string `json:"owner"`         // GitHub owner, e.g. "integrio-intropy"
	Repo          string `json:"repo"`          // e.g. "intropy-templates"
	Version       string `json:"version"`       // release tag
	DataFlow      string `json:"dataFlow,omitempty"` // NEW (uncommitted): in|out|both|internal
	Values        map[string]any `json:"values"`
}
```
- Path constant `ScaffoldRelPath = ".intropy/scaffold.json"` (line 18).
- Actual on-disk example (from `dashboard_test.go:19`): `{"schemaVersion":1,"template":"...","owner":"integrio-intropy","repo":"intropy-templates","version":"...","dataFlow":"both","values":{"appId":"int1"}}`.
- `values` typically holds `name`, `appId`, `appPort` (see `scaffold_test.go`: `{"name":"Orders","appPort":5001}`).

**The uncommitted git change** is small: it adds the `DataFlow` field, populated at create time from a template metadata label `intropy.dev/data-flow` (`DataFlowLabel`, scaffold.go lines 23, 42, 49-56). Valid values: `in`, `out`, `both`, `internal`; unrecognized → `""`. `create.go:103` sets `DataFlow: dataFlowFromLabels(tmpl.Metadata.Labels)`. Tests added: `TestDataFlowFromLabels` in scaffold_test.go. This is the *only* substantive behavior change in the modified files — it is a precedent for exactly the kind of derived-metadata-in-a-manifest the topology proposal wants.

Per-project files (AGENTS.md, Taskfile, Dapr YAMLs) are NOT hardcoded in Go — no matches for `Taskfile`/`dapr.yaml` as generated output. They come from the template skeleton. AGENTS.md/README.md/`local/dapr-components/` are only *read back* by the dashboard.

### Bottom line for the topology.json proposal
Already captured somewhere: template identity/version/owner + arbitrary `values` (scaffold.json); data-flow direction of the whole component (new `DataFlow` field); Dapr component name/type/category/direction and pipeline step names (dashboard, *derived at read-time, never persisted*); topic/binding/app-id names (C# `Constants.cs` + prose AGENTS.md only). Would be genuinely NEW: a persisted structured nodes/edges/ports graph; explicit topics/connectors/external-systems as first-class entities; any integration id (INT-042), entity, contract, or visibility fields; and any cross-component/multi-app relationships (there is currently no multi-app or cron modeling at all).
