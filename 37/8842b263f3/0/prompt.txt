### 1. "System" vs "Integration" — and the scaffold record

An **integration** is a scaffolded project: a directory containing `.intropy/scaffold.json`. That file is the authoritative record.

- Schema defined in `internal/template/scaffold.go` (`type Scaffold`):
  - `schemaVersion` (int), `template` (dir name in the blueprint repo), `owner`, `repo`, `version` (pinned template version), `values` (map).
- Constant: `ScaffoldRelPath = ".intropy/scaffold.json"`, `ScaffoldSchemaVersion = 1`.
- Real example — `tmp/testint/.intropy/scaffold.json`:
  ```json
  { "schemaVersion": 1, "blueprint": "hello-world", "owner": "integrio-intropy",
    "repo": "intropy-blueprints", "version": "v0.1.6",
    "values": { "appId": "int89", "name": "INT89" } }
  ```
  (Note: this sample uses `blueprint` where the Go struct field is `template` — the on-disk field name is `template`; treat `blueprint`/`template` as the same slot.)

A **"system" is NOT a first-class record** — it is *derived from directory nesting*. This is the key insight for your flow page. See `internal/dashboard/handlers.go`, `summarize()`:
- `Name` = the directory holding `.intropy/scaffold.json` (the integration).
- `System` = that directory's **parent** folder name.
- `Domain` = the **grandparent** folder name.
- The workspace root never counts as a system/domain; an integration directly under root has a system but no domain.

So the containment hierarchy is purely path-based: `domain/system/integration/`. The frontend groups by this in `web/src/components/FlowView.tsx` (`buildNodes`), drawing a labelled **group container** (the "system boundary" you want) per `domain/system` key, with integration cards laid out in a grid inside it. `web/src/api.ts` mirrors the contract: `Integration` has optional `system?` and `domain?`.

There is no scaffold field for "system" — if you want richer system metadata than a folder name, it does not exist yet in the model.

### 3. "Public" vs "private" APIs, and APIs at all

There is no formal `public`/`private` API taxonomy in the scaffold model, but there is a clear **convention** in the sample integrations, expressed in READMEs and endpoint code:

- `Orders/README.md` / `Demo/README.md`:
  - `POST /publish` — "the **public route you call**"; accepts `OrderIn`, publishes to pubsub component `pubsub`, topic `messages`.
  - `POST /subscribe` — "**not a route you call**"; it's the Dapr subscription handler, invoked by Dapr per message, runs the send pipeline.
- Confirmed in `Orders/src/Ingest/Endpoints.cs`: `/publish` calls `DaprClient.PublishEventAsync`; `/subscribe` is decorated `.WithTopic(PubSubName, TopicName)` + `MapSubscribeHandler()` in `Program.cs`. So "public API" = the externally-callable HTTP entry; "private" = the Dapr-internal subscribe handler.

The `match.json` / `pipeline_steps` / transport concepts are a **separate subsystem** (BizTalk migration), and they are *conceptual only in this repo* — the Go `internal/migrate/*` files they reference (`match.go`, `flow.go`, etc.) **do not exist in this checkout**; only the benchmark skill describing them does. In that model:
- A per-destination `pipeline_steps` list is emitted in a fixed order: `deserialize → extract → validate → transform → serialize → send` (SKILL.md lines ~215-231).
- Each `send`/trigger step carries a `transport` field; **every transport normalizes to `FILE`** in v1 (a non-FILE original adapter emits a `transport_override` gap).
- `processingMode` is `streamed` (both formats xml) or `poco` otherwise.
- Blueprint = `Transactional` (the only one wired). This matches the runtime C#: `Intropy.Framework.Blocks.TransactionalIntegration.Send`.

APIs are NOT modeled as a resource type the dashboard draws — the flow page draws pipeline steps and Dapr components, not HTTP routes.

### 4. How integrations connect / share resources

At the model level, integrations do **not** have explicit edges. Tellingly, `FlowView.tsx` renders `edges={[]}` — the current flow canvas draws **no connections** between integrations. Grouping (system boundary) is the only relationship expressed, and it's derived from folders.

Actual connectivity is implicit, through Dapr:
- **Pub/sub topics** are the coupling mechanism: an integration publishes to `pubsub`/`messages` and another subscribes to `pubsub`/`messages` (see the publish/subscribe split above). Two integrations sharing a `pubsub` component name + topic are effectively connected — but nothing in `scaffold.json` records that link; you'd have to infer it by matching `PubSubName`+`TopicName` (from `Constants.cs`) or component `metadata.name` across projects.
- **Shared state / databases**: `state.in-memory` statestores (e.g. `lookups`) per the biztalk skill — used for reference-data lookups (`ExtractStep`), not cross-integration sharing.
- **Bindings**: `bindings.localstorage` writes pipeline output to files (`OrderSendStep.cs` → `IFileAdapter.WriteAsync`). The `Intropy.Framework.Adapters.File` / `LocalFileAdapter` is how a pipeline's `send` block reaches a transport.
- The pipeline itself (`Orders/src/Process/OrderSendPipeline.cs`) is the intra-integration flow: `deserialize → validate → transform → serialize → send`, discovered by the dashboard from `src/Process/Steps/*.cs` filenames.
