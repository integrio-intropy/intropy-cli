# feat: xRegistry message integration

## Overview

Connect the CLI to the read-only xRegistry so `int create --subscribe
<message-ref>` wires a component to an external CloudEvents stream in one
flag, add a `message` noun for discovery, and unify internal and external
events under one vocabulary — **message** — with two resolution sources:
the registry (external) and the system's producer components (internal).
The `contract`/`topic` flat wiring keys are superseded by `subscribe` /
`publishes` blocks, read leniently during transition.

---

## Problem Frame

See origin: docs/brainstorms/2026-09-04-xregistry-message-integration-requirements.md.
Wiring values the registry already owns (CloudEvents type, pubsub, topic,
schema) are today typed by hand into template prompts, and intra-system
events are described by a different vocabulary (`contract` = C# type name
in the shared contract project) than cross-system events.

## Requirements Trace

- R1. `--subscribe` resolves ref → pubsub/topic/CE type via producing endpoint channel
- R2. Scaffold record stores `subscribe: {message, pubsub, topic, dataschema, dataschemaurl}`, list-growable shape
- R3. Block records logical `dataschema` (xid) and pinned `dataschemaurl` (version URL)
- R4. `--subscribe` against a template with no message parameters is a usage error
- R5. `message list` / `message show <ref>`, external + internal
- R6. `message list --group <id>` filter
- R7. Interactive pick list for message parameters when `--subscribe` absent
- R8. `contract` → `message` rename across values, topology, user text
- R9. Internal messages producer-declared via `publishes: {message, dataschema?}`
- R10. Assembly aggregates internal messagegroup; resolves subscriber channel from producer
- R11. `sys create/update` never contacts the registry
- R12. `registryUrl` config key + context override + `--registry-url`, no default
- R13. Degradation contract (unconfigured vs unreachable; hard fail vs fallback)

**Origin actors:** A1 (integration developer), A2 (external codegen tool), A3 (xRegistry service)
**Origin flows:** F1 (subscribe external), F2 (discover), F3 (internal wiring), F4 (codegen)

## Key Technical Decisions

- **Client consumes `/export`, not per-entity walks**: one GET yields every message, group, endpoint, and schema; the registry guarantees it byte-identical to the entity paths. Resolution (message → producer endpoint → channel) happens in-memory. Per-entity fetches stay available for `message show` freshness but are not required for v1.
- **Dual-read, never dual-write**: new scaffolds write only the `subscribe`/`publishes` block shape; readers (facts, assembly, suggestions, `mergeWiring`) accept both the blocks and the legacy flat `topic`/`contract`/`pubsub` keys. No rewrite of existing records; the legacy path dies when template releases stop emitting it.
- **`contract` semantics preserved through the rename**: today's `contract` value is a .NET type name in the shared contract project, not a CloudEvents type. The internal message block therefore carries `message` (name, doubles as the CE type) alongside the existing contract-type value during transition; the messagegroup payload to the host template keeps both fields so current host templates keep rendering. Folding the .NET type fully into the message model is template-repo work.
- **Subscriber channel resolution moves to assembly**: internal `subscribe` blocks name only the message; `Assemble` resolves pubsub/topic from the component whose `publishes` declares that message. External `subscribe` blocks carry their own snapshot and need no producer.
- **Unresolved internal subscription is a hard assembly error** naming the message and the subscribing record — a half-wired system must not render (mirrors `parseTransactional`'s both-ports-required rule).
- **Ambiguous producer resolution**: interactive runs offer a pick list of candidate channels; `--no-input` fails listing the candidates. Same rule for several producer endpoints on one message group and for a message group with no producer endpoint (error names the group).
- **`dataschemaurl` pins the schema's default version at subscribe time**; the version ID is recoverable from the URL. Re-pinning is the future re-resolve flow, not v1.
- **`--no-input` + required message parameter + no `--subscribe` fails** naming `--subscribe` — consistent with the flag's "fail rather than ask" contract.

## Open Questions

### Resolved During Planning

- Migration path for existing records: dual-read, no tooling (see Key Technical Decisions).
- Subscriber names an unpublished internal message: hard assembly error.
- Multiple producer endpoints, different channels: interactive pick; `--no-input` error listing candidates.
- `message list` internal source: workspace facts scan of scaffold records (works pre-assembly; consistent with prompt suggestions).
- `dataschemaurl` pinning: default version at subscribe time.

### Deferred to Implementation

- Exact `subscribe`/`publishes` block key names inside values (e.g. whether the CE type lives under `message` or a separate `type` key) — settle against the template repo's parameter naming when the first template declares them.
- Whether `message show` hits `/export` or the per-entity path — whichever the client already has; do not add an endpoint for cosmetics.
- Cache policy for `/export` (none vs short-lived) — measure against the local dev registry first; correctness never depends on cache.

## High-Level Technical Design

> *This illustrates the intended approach and is directional guidance for review, not implementation specification. The implementing agent should treat it as context, not code to reproduce.*

Resolution flow for `--subscribe` (F1):

```mermaid
flowchart LR
    A[int create --subscribe REF] --> B[xregistry client: GET /export]
    B --> C{resolve REF}
    C -->|message + group| D[find endpoint: usage=producer, messagegroups contains group]
    D -->|exactly 1| E[split channel pubsub/topic]
    D -->|several| F[pick list, or error under --no-input]
    D -->|none| G[error naming group]
    E --> H[resolve dataschemaxid -> schema default version URL]
    H --> I[seed values: subscribe block]
    I --> J[template.Resolve as today]
```

Record shape written into `.intropy/scaffold.json` values:

```jsonc
{
  "subscribe": {
    "message": "io.intropy.maxbo.product.export",
    "pubsub": "product-distribution-pubsub",
    "topic": "sbt-test-product-extractor-001",
    "dataschema": "/schemagroups/io.intropy.maxbo.product/schemas/product-export.v1",
    "dataschemaurl": "https://registry.intropy.io/schemagroups/io.intropy.maxbo.product/schemas/product-export.v1/versions/1"
  }
}
```

Internal publisher (R9): `"publishes": {"message": "product-exported", "contract": "ProductExported"}` —
`contract` kept during transition for the .NET shared-project type.

## Implementation Units

- [ ] U1. **xregistry client package**

**Goal:** Read-only client for the registry with in-memory resolution of message refs to wiring.

**Requirements:** R1, R3, and the resolution half of R13

**Dependencies:** None

**Files:**
- Create: `internal/xregistry/client.go`, `internal/xregistry/types.go`, `internal/xregistry/resolve.go`
- Test: `internal/xregistry/client_test.go`, `internal/xregistry/resolve_test.go`

**Approach:**
- Package doc comment states it is unrelated to `internal/registry` (OCI) — they share a name and nothing else
- Functional-options construction, `UserAgent`, context-first methods, mirroring `internal/registry/client.go`
- `Export(ctx)` GETs `/export`; typed decode of messagegroups/messages (attributes on the default version), endpoints (`usage`, `channel`, `messagegroups`), schemagroups/schemas (versions, `defaultversionid`)
- `ResolveMessage(ref)` → resolved wiring: message, CE type from `envelopemetadata.type.value`, candidate channels from producer endpoints, schema xid + default version URL
- Typed errors: message not found, no producer endpoint, ambiguous producers (carrying candidates), schema not found — callers map them to the CLI error voice
- Channel split helper `<pubsub>/<topic>` rejecting malformed channels

**Test scenarios:**
- Happy path: export fixture with one producer endpoint → resolved wiring carries pubsub, topic, CE type, dataschema xid, pinned `/versions/<default>` URL (Covers AE1's resolution half)
- Happy path: message attributes read from the default version, not the message resource
- Edge case: message ref that matches no message → `MessageNotFound` naming the ref
- Edge case: group with no producer endpoint → error naming the group
- Edge case: two producer endpoints with different channels → ambiguous error listing both channels
- Edge case: malformed channel (no `/`, empty half) → error naming the endpoint
- Error path: non-200 from registry → wrapped error naming the operation; xRegistry error body surfaced
- Error path: unreachable host → context/transport error wrapped, not panicked
- Integration: httptest server serving a captured `/export` document → end-to-end resolve

**Verification:**
- `go test ./internal/xregistry/` green; package docs explain the resolution join in the AGENTS.md comment style

## System-Wide Impact

- **Interaction graph:** value resolution (`values.go`), prompt suggestions (`suggest.go`), assembly (`blocks.go`/`assemble.go`), and `mergeWiring` all read wiring — U3's dual-read is the single seam every consumer shares; no consumer may parse blocks ad hoc.
- **Error propagation:** xregistry errors are typed at the client boundary and mapped to the CLI error voice at the command layer (front-loaded failure, remediation on the second line); assembly errors keep the strict `RecordValue` regime.
- **State lifecycle risks:** scaffold records are committed files — dual-read prevents a mixed fleet of old and new records from breaking any command; writers emit new shape only.
- **API surface parity:** the dashboard (`internal/dashboard`, `web/`) renders template fields and wiring; it reads the same facts/scaffold shapes and will show `subscribe` blocks — parity work there is follow-up, not this plan.
- **Integration coverage:** end-to-end `--subscribe` requires the template-repo PR (see Deferred to Follow-Up Work); CLI units are tested against fixtures until then.
- **Unchanged invariants:** the OCI release/template registry (`internal/registry`, `release`, `template` nouns) is untouched; `sys create/update` stays offline; legacy flat-key records remain fully functional.

## Risks & Dependencies

| Risk | Mitigation |
|------|------------|
| Template library lags the CLI, so `--subscribe` errors on every current template (R4) | Dual-read keeps everything else working; template PR is sequenced immediately after; R4 error message points at the required template release |
| `contract` means two things during transition (CE type vs .NET type) | Both fields carried in the messagegroup payload; docs mark the .NET usage transitional; full fold-in is template-repo work |
| Registry `channel` format changes (`<pubsub>/<topic>`) | Split helper validates and errors naming the endpoint; registry conformance suite owns the format |
| `/export` grows large as the registry grows | One GET per command invocation; cache policy deferred to implementation with correctness never cache-dependent |
| Registry unavailable in CI/offline demos | R11 keeps assembly offline; `message`/`--subscribe` failures carry remediation; local dev registry via `task dev` in intropy-registry |
